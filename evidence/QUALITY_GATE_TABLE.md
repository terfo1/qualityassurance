| Quality Gate ID | Metric/Criterion | Threshold/Requirement | Importance (High/Medium/Low) | Notes |
|---|---|---|---|---|
| QG-001 | Code coverage | Minimum `>= 80%` overall line/function coverage for the automated test suite | High | Justification: `80%` is a common minimum quality floor that gives broad confidence in exercised logic without implying full defect prevention. Falling below this threshold usually means important paths are untested, so the release should fail the gate until coverage is restored or formally waived. |
| QG-002 | Critical defects | `0` open critical severity defects linked to the release candidate | High | Justification: critical defects represent release-blocking risk such as data loss, security exposure, checkout failure, or system unavailability. Allowing any known critical defect would invalidate the purpose of release gating, so the threshold must remain zero. |
| QG-003 | Test execution time | Maximum `<= 10 minutes` per module/suite in CI | Medium | Justification: a ten-minute upper bound keeps feedback fast enough for frequent regression runs while still allowing realistic integration/API coverage. If a module exceeds this limit, teams tend to run tests less often, reducing defect detection value. |
| QG-004 | Regression success | `100%` pass rate for the approved regression suite with `0` failed tests | High | Justification: the regression suite exists to protect known working behavior. Any regression failure means previously validated functionality is no longer stable, so the release should fail unless the failing test is proven invalid and reclassified before approval. |
| QG-005 | Linting/static analysis | `100%` pass on configured linters and static analysis checks with `0` high-severity findings | High | Justification: linting and static analysis catch structural, maintainability, and defect-prone issues before runtime. Requiring full pass status prevents avoidable quality drift, while blocking high-severity analysis findings reduces security and reliability risk. |
